# 设计决策 / Design Decisions

这份记录解释仓库为什么采用当前结构。规则正文仍以 `README.md`、`docs/CRITERIA.md` 和 `GOVERNANCE.md` 为准。

## DD-001：只建设 GitHub 仓库

- 状态：Accepted
- 决策：阅读、提交、审核、争议和发布全部依托 GitHub 仓库能力，不建设独立官网或 GitHub Pages 目录。
- 原因：让一名维护者只维护一个事实入口，同时保留 Issue / PR 审核记录。

## DD-002：只收成果，不收工具

- 状态：Accepted
- 决策：只收可运行、可公开体验的应用或产品。AI 编程工具、IDE、编辑器、插件、模型和教程不进入项目分类。
- 原因：避免仓库退化为资源清单，保持“Vibe Coding 做成了什么”的清晰价值。

## DD-003：C1–C5 是不可互相抵消的硬门槛

- 状态：Accepted
- 决策：五项必须全部通过；Star、作者知名度、收入或社交热度不能抵消任一失败项。
- 原因：可验证性比流行度更适合作为长期收录基线。

## DD-004：结构化数据是项目事实源

- 状态：Accepted
- 决策：项目元数据只在 `data/projects.json` 维护，README 的项目区由脚本生成。
- 原因：避免中文、英文和分类目录分别手改造成漂移；让字段、排序和重复项可机械验证。

## DD-005：机器检查与人工判断分工

- 状态：Accepted
- 决策：自动化检查 URL、字段、Schema 契约、枚举、排序、重复项和双语同步；维护者人工判断 C3、C4、C5 是否真实成立。标准库校验器是合并规则的权威实现，JSON Schema 用于编辑器提示并由契约测试防漂移。
- 原因：代码风格和 200 状态码都不能证明 AI 实质参与、产品质量或真实性。

## DD-006：Issue-first 收录

- 状态：Accepted
- 决策：新增项目必须先有获批的项目提交 Issue，PR 不能绕过审核。
- 原因：将证据补充、利益冲突和拒绝理由保存在可审计的讨论中。

## DD-007：内容与代码分开授权

- 状态：Accepted
- 决策：说明和项目元数据采用 CC BY 4.0；脚本和自动化采用 MIT；行为准则保留 Contributor Covenant 的 CC BY-SA 4.0。标准文本分别保存在 `LICENSE-CONTENT` 与根 `LICENSE`，路径边界由 `LICENSING.md` 说明；根 `LICENSE` 只保留标准 MIT 文本，避免 GitHub 将说明文字误判为第三个未知许可证。
- 原因：内容复用需要署名，工程代码应易于被其他社区复用，同时尊重上游文本授权。

## 修改方式

实质改变上述决策时，先开通用 Issue 说明问题和影响，再用 PR 同步更新规则、模板、数据校验与中英文关键内容。规则变更不得为单个项目设置永久例外。
